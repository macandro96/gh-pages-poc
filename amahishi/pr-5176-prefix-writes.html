How a generation-prefix cut gets written — today, and with this PR's pipeline and writer actor

NVIDIA-NeMo/RL #5176, stacked on #4508. Permalinks pin the PR head 981376a; “today” means #4508's head 788133a.

Before
One thread does a whole cut: it freezes a batch of calls, encodes their rows one by one, writes them with the worker's own store client, waits, and only then starts the next batch.
This PR
Adds three opt-in pieces: a faster column encoder, a pipeline that prepares the next batch while one write runs (and merges batches from different cuts), and a CPU writer process that does the write.
Status
Proposed — off by default, not ready to merge. The review found CI lint red and the 78 new tests scheduled in no CI lane, and asks to reshape the config before merge.
Background. When a rollout checkpoint is saved, Gym asks each vLLM engine for a cut of every unfinished model call it lists in an inventory. Each call's new tokens become one row in TQ. A call is frozen until its row's write is confirmed, and only then does Gym get a receipt. Dotted words have a short explanation: hover or tap them.

Both paths run the same cut code: _cut_batched is now a generator that hands each batch out as a PrefixWrite and waits for its keys (recovery.py:925). With the pipeline off, checkpoint_cut answers each one right away on the same thread. With it on, run_cut gives the generator to PrefixWritePipeline, whose prepare thread steps it and whose single write thread does the writes. The figure follows one real inventory from the PR's test fixture: calls c0 (3 new tokens) and c1 (4).

Same cut, two ways to write it

Where the two paths meet, and what still differs

They meet twice. Before the write, both lanes run the same generator (steps 1–2). After encoding, both produce the same bytes (step 3); the PR's parity test checks this. They also end at the same place: the same staging rows in TQ, sealed only after the write is confirmed (step 6). What differs is only who does the work while the write runs:

Why keep both, and what the review asks

Today's path stays the default: it holds at most one batch of calls frozen and uses no extra process. The pipeline is worth its cost: the encoder plus pipeline cut the save time by about a third, far more than run-to-run noise. The writer process adds one more step, from a single run bundled with a packing change the PR itself says did not help on its own.

So the review asks to land the encoder and pipeline first, with one config block next to the existing rollout_recovery.generation_prefix_batch_* limits instead of three switches and two copied limits under vllm_cfg. It also asks to cap how far preparation runs ahead of the writes, so fewer calls stay frozen (row 5), and to move the writer process to its own PR with repeated runs. Two CI items must be fixed first: the lint check is red, and the new tests are not marked to run in the Gym test lane.
